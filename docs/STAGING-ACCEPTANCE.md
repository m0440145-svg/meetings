# إعداد الاختبار وبوابات القبول

1. إنشاء مشروع Supabase منفصل بعد مراجعة تكلفته. لا تستخدم مشروع الإنتاج أو نسخة ببيانات أشخاص حقيقيين.
2. استيراد schema baseline بعد مراجعته، وتعقب الإصلاحات كتعديلات ترحيل. أنشئ حسابات اختبار: مدير، رئيس، أمين سر، عضو لجنة أ، عضو لجنة ب، مراقب، عضو موقوف.
3. ضبط STAGING_SUPABASE_URL وSTAGING_SUPABASE_PUBLISHABLE_KEY في بيئة البناء، ثم npm run build:staging. الأداة ترفض مشروع الإنتاج. لا تضع مفتاح خدمة في الواجهة.
4. المخرجات في .staging؛ استضافتها يجب أن تستخدم مسار اختبار مستقلًا وألا تمر عبر gh-pages الإنتاجي. لا توجد بيئة حية بمجرد توليد الملفات.
5. npm test يشغّل فحوصًا محدودة للأداة والمصدر؛ لا يثبت صحة RLS أو الإرسال أو دورة الاجتماع.

| الاختبار | النتيجة المطلوبة |
|---|---|
| غير مسجل/موقوف/مراقب يحاول تعديلًا مباشرًا | رفض من قاعدة البيانات، وليس إخفاء الزر فقط |
| عضو أ يطلب اجتماع/ملف لجنة ب بالمعرف | رفض؛ لا تسريب عبر البحث أو Realtime أو signed URL |
| تغيير حقول الصلاحية من العميل | رفض؛ لا ترقية ذاتية |
| اجتماع بلا نسبة نصاب | رفض الحفظ |
| اجتماع ثم مرفق ثم تنزيل من جهاز ثانٍ | تطابق hash الملف وارتباطه بالاجتماع |
| الدعوة والاعتذار والتوكيل | رابط فردي محدود الصلاحية وقابل للإلغاء؛ لا ازدواج |
| التصويت قبل النصاب وبعد الإغلاق | رفض؛ الصوت المتزامن لا يتكرر |
| التصويت السري | لا يمكن قراءة اختيار العضو عبر API أو سجل التدقيق |
| توقيع محضر ثم محاولة التعديل | رفض تغيير النسخة المختومة؛ إصدار تصحيحي مستقل |
| إعادة webhook التوقيع | لا تكرار ولا تغيير حالة بلا تحقق HMAC |
| إرسال متزامن/مهلة مزود | لا ازدواج؛ حالة معلّقة صحيحة؛ تأكيد التسليم منفصل |
| اعتماد المحضر ثم إنشاء قرار ومهمة | ارتباطات محفوظة ومسؤول ومهلة وأدلة وتاريخ تغييرات |
| استرجاع نسخة قاعدة وتخزين | استرجاع في وجهة معزولة ومطابقة أعداد وhashes وروابط |

لكل اختبار سجل: commit، بيئة الاختبار، الدور، الوقت، مدخلات غير حساسة، المتوقع، الفعلي، ودليل. لا تضع نتيجة نجاح قبل تنفيذ الاختبار.
