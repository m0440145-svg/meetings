# تجهيز الاستضافة

هذه الحزمة قابلة للبناء والتشغيل كواجهة مستضافة، وليست إقرارًا باكتمال جاهزية التشغيل المؤسسي. قاعدة البيانات تبقى Supabase؛ نقل الواجهة إلى Railway لا ينقل البيانات ولا يصلح صلاحياتها تلقائيًا.

## ما تم تجهيزه
- `npm run build`: يخرج ملفات الواجهة فقط إلى `dist`، دون SQL أو الاختبارات أو الأسرار.
- `npm start`: يشغل خادم الملفات على PORT الذي تعينه الاستضافة (3000 محليًا).
- `railway.json`: تثبيت مقفل، اختبار، بناء، تشغيل وفحص صحة الصفحة الرئيسية.
- مسار GitHub Pages أصبح يدويًا من main وبعد الاختبارات وتأكيد اجتياز قبول قاعدة البيانات. لا يحدث النشر عند كل push.
- لا تغييرات على التصميم أو CSS أو الخطوط.
- البريد الخارجي وواتساب والتوقيع الرسمي مؤجلة. أزرار الإرسال معطلة، واستدعاء المعالجة لا يرسل، والدعوات الجديدة لا تضيف رسائل WhatsApp إلى الطابور.
- تبقى الرسائل القديمة في قاعدة البيانات دون حذف. وظائف الخادم المنشورة سابقًا لم تُعدّل أو تُعطّل؛ يجب إيقاف أي مجدول خارجي لها في إعدادات المشروع إن وُجد. تعطيل الواجهة ليس قيدًا أمنيًا على API.

## إعداد Railway
1. استخدم فرع المراجعة لبيئة تجريبية، دون توجيه الدومين التشغيلي إليه قبل القبول.
2. عيّن متغيري `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY` إلى مشروع الاختبار المستقل.
3. شغّل البناء والتشغيل بالأوامر في railway.json. يفشل البناء إذا غاب الإعداد أو مُرر مفتاح سري.
4. أضف الدومين الناتج إلى Supabase Auth Site URL وRedirect URLs وفق البيئة. تحقق من تسجيل الدخول والخروج وإعادة تعيين كلمة المرور.
5. لا تضع service_role أو مفاتيح المزودين ضمن هذه الخدمة الأمامية.

## إعداد GitHub Pages
بعد اعتماد الإصدار ودمجه فقط: اضبط متغيري المشروع في GitHub environment المسمى production، ثم شغّل Publish reviewed website يدويًا. يجب إعداد قواعد مراجعة environment لدى GitHub؛ وجود الاسم في YAML لا يفرض مراجعين تلقائيًا.

## التحقق المنفذ
`npm test` يختبر البناء وعزل محتويات الحزمة، خادم HTTP ومنع مسارات العبور والملفات غير المنشورة، تأجيل التكاملات، واختبارات RLS المحلية السابقة.
فحص `/` اختبار استجابة الخادم فقط، وليس اتصال قاعدة البيانات أو صلاحية المستخدم.

## بوابات القبول المتبقية قبل استخدام بيانات حقيقية
- تطبيق ترحيل الصلاحيات على مخطط Supabase كامل في بيئة منفصلة واختباره. SQL في database/proposals ما زال مقترحًا.
- نقل الوظائف التشغيلية المحلية وحصر بيانات المتصفح وترحيلها دون فقد.
- اعتماد ضوابط النصاب والتصويت والمحاضر والتدقيق الخادمي.
- اختبار النسخ الاحتياطي والاسترجاع ودورة اجتماع كاملة بحسابات مستقلة.
- اختبار البريد وواتساب والتوقيع لاحقًا كما طلب المستخدم، قبل تفعيلها. خدمات مصادقة Supabase البريدية مستقلة عن رسائل دعوات المنصة وتحتاج إعدادها إذا استُخدمت OTP أو استعادة كلمة المرور.

## التراجع
أعد نشر آخر commit مقبول للواجهة. لا تعكس ترحيل قاعدة البيانات ولا تحذف سجلات جديدة تلقائيًا عند التراجع. احتفظ بنسخة قاعدة البيانات وبنسخة كائنات Storage منفصلة، واختبر الاسترجاع قبل أي ترحيل إنتاج.
